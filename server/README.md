# NLP-HAZOP

A research prototype for recovering missing endpoints in structured HAZOP causal relationships. The system compares prompt-only LLM reasoning, sparse vector retrieval, graph reasoning, and a hybrid graph + vector + LLM strategy.

> **Research caveat:** the benchmark labels currently available in this repository are row-derived *silver associations*. They are not independently expert-validated causal ground truth. Report results as exploratory recovery of worksheet associations, not proof of causal correctness or plant safety.

## Research methods

| Method | Implementation | Input available to method | Output |
|---|---|---|---|
| Prompt-only LLM | PromptOnlyReasoner | Held-out scenario metadata and query only | Model-inferred endpoint or abstention |
| Vector retrieval | TfidfRetriever | Training-corpus records indexed with sparse TF–IDF | Ranked row-associated endpoint candidates |
| Graph reasoning | GraphReasoner + GraphNeighborhoodRetriever | Typed causal edges from training scenarios in the same plant/process family | Direct evidence candidate or bounded multi-hop path hypothesis |
| Hybrid | HybridRetriever + HybridReasoner + LLMReasoner | TF–IDF candidates plus graph-derived path candidates | LLM adjudication with provenance-aware evidence |

The vector baseline is a transparent **TF–IDF sparse-vector** implementation. It is not a dense embedding model and does not use Qdrant. The graph implementation uses the repository abstraction and an in-memory adapter; Neo4j persistence is not required to reproduce these experiments.

### Provenance model

Relationships carry an explicit origin:

- source: directly attributed to a source.
- reconstructed: reconstructed from a published case; not verbatim source rows.
- synthetic: generated/simulated scenario data; not source evidence.
- expert: attributed to expert review; an individual relationship is verified only when its own relationship-level validation status is explicit.
- retrieval_inferred: candidate generated by retrieval from row co-occurrence.
- graph_inferred: indirect path hypothesis composed from graph edges.
- model_inferred: model-only proposal.
- unspecified: default for datasets or records whose origin cannot be established from provenance or record-type fields.

The supplied T-301 and DWSIM datasets contain no expert-validated relationships. Record-level `Validation_Status=validated` does not validate every relationship in that row. `is_expert_verified` is set only when the row has an expert origin and an explicit `Relationship_Validation_Status` (or supported edge-level alias) of `validated`. A conflicting expert record type with an unvalidated record status is demoted to unspecified; a validated expert record without edge-level validation remains attributed to expert review but its individual relationships are not marked verified. Notes such as “Review required” and “Scope caveat” remain notes, not validation.

## Datasets

Datasets are stored separately and benchmarked separately. Scenario identity is the composite `(dataset_id, scenario_id)`, so the same scenario label (for example `S001`) can exist in two uploaded datasets without overwriting either record. Relationship source IDs include the dataset, scenario, CSV row, and relationship field/index. Retrieval and TF–IDF indexing are scoped to one dataset per request; corpora are never mixed by default.

| Track | File | Rows | Provenance |
|---|---|---:|---|
| T-301 reconstructed | data/raw/t301/T301_HAZOP_CCPS2001_style.csv filtered to PAPER_REPORTED_RECONSTRUCTION | 40 | Reconstructed from the reported T-301 case in Single et al. (2020); not a verbatim transcription |
| T-301 synthetic | Same file filtered to SYNTHETIC_CONTINUATION | 54 | Synthetic continuation; not attributable to the paper |
| DWSIM synthetic | data/raw/dwsim/synthetic_hazop_D001_D030.csv | 30 | Synthetic/simulation-derived scenarios; review and scope caveats remain |

data/raw/dwsim/HAZOP_DWSIM30_worksheet_format.csv is a worksheet-style export of the D001–D030 synthetic DWSIM scenarios. It is an alternate representation, not an additional independent set of 30 scenarios. The canonical benchmark input is synthetic_hazop_D001_D030.csv.

The DWSIM validation-note values present in the source are retained in record remarks: 16 “Review required”, 6 “Scope caveat”, 6 “NEEDS_MODEL_REVISION”, 1 “Review reaction model”, and 1 “NEEDS_REVIEW”. None is silently promoted to expert validation.

### Graph construction from a row

The importer maps row fields into typed edges:

- cause --causes_deviation--> deviation
- If a single simulated/inferred intermediate effect is present: deviation --leads_to--> effect --leads_to_consequence--> consequence
- If multiple intermediate effects are present: deviation --leads_to--> effect for each effect, and deviation --co_occurs_with_consequence--> consequence (avoiding arbitrary positional `zip` or Cartesian product pairings between intermediate effects and consequences)
- If no intermediate effect is present: deviation --leads_to_consequence--> consequence

These edges preserve the row origin and source/scenario identifier. Their evidence text states that they are row-level associations, not independent causal validation. Composed paths are returned with origin graph_inferred, the full path, and no fabricated confidence value.

Malformed rows with missing or extra cells preserve row numbers, missing columns (with `None` values and `_missing_columns`), and extra cells (under `_extra_cells` in raw rows), surfacing structured warnings in the preview API.

## Leakage-aware benchmark

The runner performs a deterministic **scenario-level** train/test split (default 80/20, seed 42). All queries derived from a scenario stay in the same split.

For held-out scenarios, the retrieval repository contains a metadata-only record. Causes, consequences, safeguards, recommendations, remarks, and causal edges are removed from that target record. Graph neighbourhoods and TF–IDF indices are built from training scenarios only. The target row is used only to construct its query and silver answer set.

One query is created for each listed cause in a held-out row. The answer set contains the consequences co-listed in that same row. Since the source rows do not specify independently adjudicated cause-to-consequence pairs, all co-listed consequences are treated as candidate silver endpoints for each cause. This definition is explicit in output metadata and must not be described as expert ground truth.

### Metrics

The output reports:

- Micro and macro precision, recall, and F1.
- Hit@1 and mean reciprocal rank (MRR).
- Coverage and abstention rate.
- Mean number of candidates.
- Evidence-text availability and provenance-origin rates.
- Mean per-query latency and TF–IDF index-build time.
- cost_usd, left null because the current Groq wrapper does not capture billable token usage reliably.

LLM methods use the same deterministic capped query subset (max-llm-cases) to limit API calls. If GROQ_API_KEY is unavailable, the prompt-only and hybrid methods are marked skipped; the script does not substitute fake model outputs.

## Reproduce the benchmark

Run each dataset as a separate experiment:

~~~bash
cd server
uv run python -m scripts.run_benchmark --dataset t301-reconstructed
uv run python -m scripts.run_benchmark --dataset t301-synthetic
uv run python -m scripts.run_benchmark --dataset dwsim-synthetic
~~~

Enable prompt-only and hybrid LLM calls (requires GROQ_API_KEY):

~~~bash
uv run python -m scripts.run_benchmark \
  --dataset t301-reconstructed \
  --with-llm \
  --max-llm-cases 10
~~~

Useful controls:

- --test-fraction 0.2
- --seed 42
- --top-k 10
- --max-hops 4
- --limit-cases 20 for a quick smoke run
- --output-dir ../results/custom-run

By default, the runner writes to the repository-root `results/<dataset>/`
directory (one level above `server/`). A relative custom `--output-dir`
is resolved from the current working directory.

Each run writes:

- results.json: metadata, per-method aggregate metrics, and per-case predictions.
- summary.csv: compact method comparison.
- predictions.csv: one row per query and method.

Generated result files are not committed as canonical findings. The 30 October 2026 exploratory baseline is summarized in
`../reports/benchmark-baseline-2026-10-30.md`; its raw JSON/CSV files are uploaded
as separate GitHub Actions artifacts for each dataset track. The baseline run
used seed 42 and did not enable the LLM methods. Causal correctness claims still
require a separately expert-adjudicated held-out set.

## Current limitations and next research requirements

1. **Silver-label limitation:** row co-occurrence cannot establish that every listed cause produces every listed consequence. Expert adjudication is required before claiming causal correctness.
2. **Dataset limitation:** T-301 has only 40 reconstructed and 54 synthetic rows; DWSIM has 30 synthetic scenarios. Do not pool them, and do not train or evaluate a large model on these small data as if they were representative.
3. **Vector limitation:** TF–IDF is lexical and does not provide semantic embeddings. A dense embedding + vector database comparison is a separate future experiment and should be reported as such.
4. **Graph limitation:** paths compose typed cause/deviation/effect/consequence edges. They express indirect reachability, not proof that the endpoints form a direct causal edge.
5. **LLM limitation:** outputs are model-inferred and may abstain; confidence is model-reported, not calibrated probability. API latency is measured, but token cost is not yet captured.
6. **Validation still required:** have HAZOP experts adjudicate a held-out subset, define relation-level evidence criteria, measure annotation agreement, and report performance on expert-validated labels separately from synthetic/reconstructed silver labels.
7. **Safety boundary:** this is a research aid, not an operational HAZOP tool or safety recommendation generator. Engineering decisions require qualified review.


## Local FastAPI upload API

The preview endpoint accepts a UTF-8 HAZOP CSV and returns a normalized, temporary
preview. It does not persist records. After reviewing that preview, the client can
explicitly confirm the dataset through `POST /api/v1/datasets/import`; confirmed
imports persist dataset metadata, full normalized scenario payloads (including raw
row provenance), and typed concept relationships in Neo4j.

From the `server/` directory:

```bash
uv sync
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

- Health check: `GET http://127.0.0.1:8000/health`
- CSV preview: `POST http://127.0.0.1:8000/api/v1/datasets/preview`
- Interactive API docs: `http://127.0.0.1:8000/docs`

Send the file as multipart form data using the field name `file`. The default
preview returns up to 100 normalized records; `preview_limit` can be set from
1 to 500. Uploads are limited to 10 MB and must be UTF-8 CSV files (UTF-8 BOM
is supported) containing `Scenario_ID` (or `Scenario ID`) and `Deviation` columns.

### Ingestion and normalization capabilities

- **Parenthetical preservation:** List-valued fields (safeguards, recommendations, causes, consequences, effects) do not split commas or semicolons inside balanced parentheses or brackets. Explanatory annotations (e.g. `OverfillProtection (reported/ontology safeguard concepts, actual installation status requires source interpretation)`) are preserved intact with their item.
- **Effects and intermediate states:** Recognizes `effects` and aliases (`Intermediate Effect`, `Intermediate_Effects`, `Simulated_or_Inferred_Effect`, etc.) and maps multi-step chains (`deviation -> leads_to -> effect -> leads_to_consequence -> consequence`) without inventing phantom effects or creating arbitrary Cartesian products.
- **Row-level provenance and lossless data:** Records preserve the exact 1-based CSV `row_number` and the complete `raw_row` dictionary alongside normalized values.
- **Explicit relationship semantics:** Generated relationships carry their explicit origin (`reconstructed`, `synthetic`, etc.), evidence clarifying that they are row-level associations, and `is_expert_verified: false`.
- **Inspection transparency:** The preview response exposes:
  - `recognized_columns`: Canonical HAZOP fields matched to CSV headers.
  - `unrecognized_columns`: Non-empty headers not mapped to standard fields.
  - `missing_expected_columns`: Standard fields (causes, consequences, safeguards, equipment) missing from the CSV.
  - `persisted: false` and `storage: "not_persisted"`.
  - `summary`: Counts of rows read, records loaded, rows skipped, record types, validation statuses, and detailed breakdowns of relationships by origin and predicate.
  - `warnings`: Explanatory warnings regarding unverified row-level associations, unrecognized columns, missing expected columns, skipped rows, or malformed lines.

The default CORS allowlist supports the Vite development server and common Tauri origins; set `NLP_HAZOP_CORS_ORIGINS` to add comma-separated origins when needed.

The dependency lockfile is refreshed by `uv sync` when project dependencies
change. After adding or changing dependencies, run `uv lock` locally and
commit the updated `uv.lock` for a fully reproducible dependency snapshot.


## Persistent API and Neo4j storage

The API keeps the preview and persistence boundaries explicit:

- `POST /api/v1/datasets/preview`: validate and preview; never writes to storage.
- `POST /api/v1/datasets/import`: explicit confirmation endpoint. Accepts multipart
  `file`, optional `dataset_id`, and optional `name`. Stores metadata, normalized
  scenarios, raw row/provenance fields, and typed causal edges in one Neo4j
  transactional HTTP commit. A dataset ID is immutable after creation; duplicate
  imports return HTTP 409. Scenario IDs must be unique within a dataset.
- `GET /api/v1/datasets` and `GET /api/v1/datasets/{dataset_id}`: list and inspect
  persisted dataset metadata.
- `GET /api/v1/datasets/{dataset_id}/scenarios`: list scenarios; optional
  `equipment`, `deviation`, and `limit` filters.
- `GET /api/v1/datasets/{dataset_id}/scenarios/{scenario_id}`: fetch one scenario.
- `GET /api/v1/datasets/{dataset_id}/relationships`: query typed relationships by
  optional `subject`, `predicate`, and `object`.
- `GET /api/v1/datasets/{dataset_id}/graph`: return nodes and edges suitable for a
  graph visualization.
- `POST /api/v1/datasets/{dataset_id}/recovery`: retrieve scenario-local and
  same-dataset cross-scenario evidence, enrich with a bounded graph neighborhood,
  and return candidates plus a graph-reasoning proposal or abstention.

### Configure Neo4j

The adapter uses Neo4j's transactional HTTP endpoint through the existing `httpx`
dependency. Configure all three required environment variables before starting
the API:

```bash
export NEO4J_HTTP_URI="http://127.0.0.1:7474"
export NEO4J_USERNAME="neo4j"
export NEO4J_PASSWORD="your-local-password"
export NEO4J_DATABASE="neo4j"  # optional; defaults to neo4j
export NEO4J_TIMEOUT_SECONDS="15"  # optional
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Use the HTTP URI (normally port 7474), not a `bolt://` URI. The adapter creates
dataset, dataset-scoped scenario, and dataset-scoped concept uniqueness constraints
on first use. Dataset creation, scenario writes, and edge writes are sent in one
transactional commit. The original uploaded CSV bytes are not stored as a separate
file; source filename and SHA-256 are retained, and every normalized record keeps
its raw row and row number.

Without Neo4j settings, the server still starts and `/health` plus CSV preview
remain available. Confirmed import and dataset/graph/recovery endpoints return
HTTP 503 rather than silently using process-local memory. The in-memory repository
remains the deterministic adapter for unit tests and benchmark experiments.

Recovery responses are hypotheses only. Silver row associations, graph paths,
and model outputs are not expert-validated causal truth. The API never stores a
recovery proposal as an expert-verified edge.
